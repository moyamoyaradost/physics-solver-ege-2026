### 1.2 Принципы архитектуры

#### Модульность
- Каждый модуль решает свою задачу
- Модули независимы друг от друга
- Четкие интерфейсы между модулями

#### Разделение ответственности
- **Презентационный слой** - отображение данных
- **Слой бизнес-логики** - решение задач
- **Слой утилит** - вспомогательные функции
- **Слой платформы** - Web API

#### Переиспользование
- Общие утилиты используются всеми модулями
- Общие стили применяются ко всем компонентам
- Единообразный подход к решению задач

### 3.2 Потоки данных

#### Инициализация модуля задачи:
1. Загрузка HTML

3. Загрузка `canvas-utils.js` → доступ к утилитам

5. Инициализация Canvas через `getCanvas()`
6. Получение контекста через `getContext()`

1. Обновление состояния (время, параметры)
2. Очистка Canvas через `clearCanvas()`
3. Отрисовка элементов через Canvas API
4. Использование утилит (`drawArrow()`, `drawAxes()`)
5. `requestAnimationFrame()` для следующего кадра

## 4. Паттерны проектирования

### 4.1 Модульный паттерн
Каждый файл представляет собой независимый модуль:
```javascript
// canvas-utils.js - модуль утилит
function getCanvas(id) { ... }
function getContext(id) { ... }
// Экспорт через глобальную область видимости
```

### 4.2 Фасад
`canvas-utils.js` предоставляет упрощенный интерфейс к Canvas API:
```javascript
// Вместо:
const canvas = document.getElementById('id');
if (!canvas) throw new Error('...');
const ctx = canvas.getContext('2d');
if (!ctx) throw new Error('...');

// Используем:
const canvas = getCanvas('id');
const ctx = getContext('id');
```

### 4.3 Утилитный паттерн
Набор независимых функций без состояния:
```javascript
// Функции не зависят друг от друга (кроме базовых)
safeDivide(a, b, 0);  // Независимо
drawArrow(ctx, ...);  // Независимо
```

## 5. Принципы SOLID в проекте

### 5.1 Single Responsibility Principle (SRP)
- `canvas-utils.js` - только работа с Canvas
- `common.css` - только стили
- Каждый модуль задачи - только одна задача

### 5.2 Open/Closed Principle (OCP)
- Модули открыты для расширения (добавление новых задач)
- Закрыты для модификации (общие утилиты не меняются)

### 5.3 Liskov Substitution Principle (LSP)
- Все модули задач используют одинаковый интерфейс
- Можно заменить один модуль задачи другим без проблем

### 5.4 Interface Segregation Principle (ISP)
- Утилиты предоставляют только необходимые функции
- Нет "толстых" интерфейсов

### 5.5 Dependency Inversion Principle (DIP)
- Модули задач зависят от абстракций (утилиты)
- Не зависят от конкретных реализаций

## 6. Метрики архитектуры

### 6.1 Связанность (Coupling)
- **Низкая связанность** - модули слабо связаны
- Модули задач не зависят друг от друга
- Зависимость только от общих утилит

### 6.2 Сплоченность (Cohesion)
- **Высокая сплоченность** - каждый модуль решает одну задачу
- `canvas-utils.js` - только Canvas утилиты
- `common.css` - только стили

### 6.3 Модульность
- **20 модулей задач** - независимые модули
- **2 общих модуля** - переиспользуемые утилиты
- **1 модуль навигации** - точка входа

3. Реализовать логику задачи

### 7.2 Расширение утилит
1. Добавить функцию в `canvas-utils.js`

3. Использовать в задачах

### 7.3 Добавление новых стилей
1. Добавить стили в `common.css`
